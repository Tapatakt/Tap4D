# Tap4D — v2: рендерер с честной (радиальной) перспективой

## Мотивация

При планарной пинхол-проекции (деление на Z) перспектива есть только вдоль оси взгляда:
стрейф по W лишь сдвигает объекты по цветовой оси, но красные и синие части объекта
не расходятся на экране. Хочется W-параллакс: положение точки на экране должно
зависеть от её W через реальное расстояние до глаза.

## Ключевая идея: воксельный рейкастинг вместо плоского пересечения

При радиальной проекции виртуальный экран — сфера направлений. Прообраз виртуального
пикселя (sx, sy, sw) — **луч** из глаза. Прообраз реального пикселя (sx, sy) —
конус (семейство лучей по sw). Поэтому:

- ось ана-ката виртуального экрана дискретизируется на **срезы** (параметр: число срезов,
  диапазон = диапазон палитры — экран по-прежнему конечный по W);
- каждый виртуальный пиксель (x, y, срез w) = один луч с фиксированным направлением;
- пересечение луча с тетраэдром — та же линейная алгебра, что сейчас (4 уравнения,
  5 неизвестных, нуль-пространство + допустимый интервал), просто направление фиксировано
  полностью — код даже проще нынешнего TetraPixelIntersection;
- **окклюзия становится физически правильной**: внутри виртуального пикселя побеждает
  ближайший по лучу — независимо от других срезов;
- реальный пиксель (x, y) показывает все срезы, где был хит, чередуя их по кадрам;
  цвет среза = цвет палитры (интерполяция внутри среза не нужна — срез и есть цветовой бин).

## Что это даёт даром

- W-параллакс: стрейф по ана-ката разводит части объекта на экране.
- Исчезает tie-шум кандидатов (кандидаты — срезы, а не тетраэдры; два тетраэдра
  на одном луче честно окклюдируют по t).
- Исчезает потребность в near-plane/W-клиппинге геометрии (t > near на луче,
  срезы вне диапазона просто не существуют) и в ε-расширении для стыков.
- Исчезает проблема «концы сегмента пересечения» (сегментов пересечения больше нет).

## Что меняется

1. `Rendering/Raycast*`: RayTetrahedronIntersection (линейно, closed form),
   RaySegmentIntersection (луч–цилиндр 4D: минимум квадратичной формы по (t, t') —
   закрытая формула).
2. Срезы: параметр сцены/рендерера (count + диапазон); палитра отображает индекс среза.
3. Чередование: кандидаты пикселя = срезы с хитом (в порядке срезов или по глубине —
   открытый вопрос, см. ниже).
4. FOV: направления с sx²+sy² > f² за полусферой — углы квадратного экрана тёмные
   (либо ограничить угол обзора).
5. GPU: два прохода, см. раздел «Двухпроходный GPU-рендер».
   Буферов геометрии столько же, плюс воксельный буфер экрана.

## Что остаётся

- Camera4, Rotation4, GeometryTransform, Tesseract, Scene4 — без изменений.
- Палитра, вьювер, FPS-контроллер — без изменений (рендерер сменится за интерфейсом
  IRenderer; добавить переключение планарный/радиальный по клавише).
- Процесс: сначала CPU-референс + тесты, потом GPU-порт + сверка, потом снапшоты.

## Двухпроходный GPU-рендер

Шейдер делится на две части, между которыми — трёхмерный буфер виртуального экрана:

- **Pass 1 (рейкастинг)**: поток на воксель (x, y, срез w) → буфер состояний
  вокселя: пусто / заблокировано заслонкой / хит (глубина + покрытие).
  Окклюзия по-лучевая: заслонка блокирует только лучи, реально проходящие через неё
  (для выпуклого тела это даёт корректное удаление скрытых линий у wireframe).
- **Pass 2 (композитинг)**: поток на реальный пиксель → собирает срезы с хитом,
  чередует по номеру кадра, красит палитрой (яркость = покрытие).

Бонусы: при смене кадра чередования pass 1 не нужен (мерцание почти бесплатно);
срезы можно дампать для отладки; pass 1 — точка подключения будущего BSP.
Память: 800×800×32×4 байта ≈ 65 МБ — приемлемо.

## Покрытие (антиалиасинг по ана-ката)

Разрешение по W низкое, поэтому яркость пикселя масштабируется долей конуса пикселя,
реально покрытой объектом. Реализация — суб-сэмплинг по W в pass 1: K лучей внутри
среза, доля попаданий = покрытие (параметр, можно выключить). Заодно сглаживает
границы срезов: объект на стыке срезов зажигает оба пропорционально.
Аналитическое покрытие (границы φ-интервала в закрытой форме) — возможное
будущее уточнение, но громоздкое.

## Открытые вопросы

- Число срезов (32? 64?) — баланс гладкости цвета и производительности; замерить.
- Число суб-лучей на срез (1/2/4) — баланс гладкости яркости и производительности.
- Порядок чередования срезов на пикселе: по W или по глубине ближайшего хита.
- Оставить ли планарный рендерер навсегда как режим (предлагаю: да, по клавише).

## Отвергнутые варианты

- Непрерывный радиальный солвер (ближайшая точка тетраэдра на квадратичном конусе
  пикселя): нет закрытой формы, нужен Newton на каждый пиксель-тетраэдр — медленно
  и хрупко. Воксельная дискретизация решает ту же задачу линейно.
- Поворотная (per-vertex) нормализация на сферу с плоским пайплайном: быстро,
  но приближённо и с артефактами на силуэтах; годится как предпросмотр, не как цель.
